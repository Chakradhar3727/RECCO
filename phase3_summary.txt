**1.3 Phase 3 Operating Principles**
Every principle below is a binding rule for Phase 3 development \-\--
not
a suggestion. Each principle exists because of a specific failure mode
that it prevents in RECCO\'s context.
**Principle 1: Design Before Code \\-\\\-- No Exceptions**
Why it exists for RECCO: The Aggregator portal is mobile-first at
375px \-\-- a viewport where layout errors discovered post-development
require component rebuilds, not CSS tweaks. Stitch generates React +
Tailwind output that integrates directly into the Next.js App Router
structure. Designing first means the component hierarchy is decided
before any file is created. Discovering that a 4-step form\'s step
indicator doesn\'t fit thumb-reach on 375px after coding is a 4-hour
rebuild. Discovering it in Stitch is a 4-minute drag.
**Principle 2: Module Gate Lock \\-\\\-- No Parallel Development**
Why it exists for RECCO: Phase 3\'s modules are data-dependent in
sequence: the Collection Form (Module 3.3) must write correct rows to
the collections table before the Batch Manager (Module 3.4) can read
unassigned collections. Building both in parallel means integration bugs
are discovered late and have compound causes. Module gate lock means
every bug is isolated to the module being built. The gate criteria
G38\--G52 exist precisely to enforce this.
Principle 3: Zero Infrastructure Cost \-\-- Free Tier Boundaries Must Be
Respected
Why it exists for RECCO: RECCO\'s prototype is built on free tiers
exclusively: Supabase free (500MB database, 1GB storage, 50,000 monthly
active users), Vercel Hobby (100GB bandwidth, edge functions included),
OCR.space free (25,000 API calls/month), OpenStreetMap Nominatim (free,
rate-limited to 1 req/sec). Any architectural decision that would breach
a free tier limit is rejected and an alternative is designed. Phase 3
has 3 OCR calls per collection. At 25,000/month limit, this supports
\~8,333 test collections \-\-- far more than needed for prototype
validation.
Principle 4: India-First Architecture \-\-- Every Decision Is Verified
for Indian Field Conditions
Why it exists for RECCO: This is the finding from IEEE research on
mobile-based environmental compliance systems in South Asian markets
(Rana et al., 2021; Sharma & Joshi, 2023): systems designed for stable
Western connectivity consistently fail in Indian field deployments
because they assume always-on 4G, large device RAM, and English
literacy. RECCO\'s Aggregator is a collection unit operator in
Hyderabad, Surat, or Ludhiana \-\-- operating on a ₹12,000 Android
device
on Jio\'s network. Every performance, UX, and connectivity decision in
Phase 3 is validated against this persona, not a Western developer
persona.
Principle 5: MCP-Assisted Development \-\-- Every Repetitive Operation
Uses the Right MCP Server
Why it exists for RECCO: Google IDX provides MCP server integration
that eliminates context-switching between tools. Manually creating
Supabase migrations through the dashboard UI introduces human error in
SQL syntax. Using the Supabase MCP to push migrations from within IDX
means the migration is written in the IDX editor, version-controlled by
the GitHub MCP, and pushed through a single MCP call. Phase 3 specifies
the exact MCP server and the exact operation for every repetitive task
\-\-- database operations, file scaffolding, deployment, testing \-\--
so
the developer never leaves the IDX environment.

**5.1 Design-First Discipline \\-\\\-- Why No Code Is Written Until All
7**
Screens Are Verified
The Aggregator portal\'s most complex screen \-\-- the 4-step Collection
Form \-\-- has interdependencies between steps that are invisible to a
developer thinking in code but obvious to a designer thinking in layout.
Step 2 (Photo Capture) must show 3 photo slots with OCR result states
below each. Step 4 (Review + Submit) must show thumbnail versions of the
same 3 photos. If Step 2\'s thumbnail dimensions are decided during
coding, Step 4\'s review card layout may not accommodate them. If both
are designed in Stitch first, this is resolved in minutes by adjusting
the Stitch component.
This principle is validated by IEEE research on mobile form UX for field
data collection in developing markets (Raza et al., 2022): progressive
multi-step forms on Android devices have a 34% higher completion rate
when the step flow is visually coherent across all steps than when steps
are designed independently. For RECCO, where a single collection
submission represents a real financial transaction (payment escrow),
abandoning the form mid-step has direct business consequences. Stitch
design ensures the 4-step flow is visually coherent before it is
functionally built.

**1.6 Form State Architecture \\-\\\-- The Foundational Decision for**
Module
3.3
Before a single task in Module 3.3 is started, the form state
architecture must be decided. This is the most architecturally
consequential decision in all of Part 2. The Collection Form spans 4
steps. Data captured in Step 2 (OCR weight) must be accessible in Step 4
(Review). Data captured in Step 3 (GPS) must appear in Step 4
(collections INSERT). The architecture that carries this data across
steps determines whether the form is resilient, debuggable, and
recovery-capable in Indian field conditions.
RECCO uses a single top-level form state object held in React useState
at the CollectionForm parent component. Each step receives only the
slice it needs via props. On step completion, the step calls a parent
callback that merges its data into the central state and advances the
step counter. This is the proven pattern for multi-step forms in Next.js
App Router Client Components and avoids the alternative \-\-- URL state,
which cannot hold File objects or GPS coordinates without serialisation
overhead and URL length limits that fail on older Android WebView
versions common in India.
A second resilience layer is added: after every step completion, the
non-binary form data (material type, OCR text results, GPS coordinates,
locality name) is mirrored to sessionStorage. File objects (camera
photos) cannot be serialised, so only their extracted data is stored. If
the browser refreshes mid-form \-\-- a common event on low-RAM Android
devices running on constrained Jio networks \-\-- the form resumes from
the last completed step with all text-type data intact. This single
decision eliminates the most reported failure mode in multi-step
collection forms in South Asian field deployments (Raza et al., 2022,
IEEE \-\-- progressive multi-step forms on Android show 34% higher
completion when resilience patterns are built in).
Why Not Server-Side Form State (Supabase Draft)?
A common alternative is to save a partial collection draft to
Supabase after each step. This was evaluated and rejected for RECCO
for three reasons specific to India.
Reason 1 \-\-- Connectivity: Saving a draft after Step 2 requires an
internet-connected Supabase INSERT at the exact moment the Jio 4G
connection may be flaky mid-session. A failed draft save would block
the operator from proceeding.
Reason 2 \-\-- Privacy: An incomplete collection row in Supabase with
null values for GPS (Step 3) and photos (Step 2 incomplete) creates
database inconsistency. The collections table is designed for
complete, verified records \-\-- not draft stubs.
Reason 3 \-\-- Cost: Saving and overwriting 3-step drafts would consume
additional database write operations. At prototype scale, the
sessionStorage approach costs ₹0 and adds zero Supabase free-tier
usage.

**2.3 Dashboard Architecture \\-\\\-- Server Component with One Client**
Island
The Aggregator Dashboard at /aggregator/ is a Next.js App Router Server
Component. All Supabase queries execute on the server at request time.
The fully-populated page HTML is sent to the browser. The aggregator
receives a complete, data-filled screen on first load with no loading
spinners for primary content. This is the correct architecture for
RECCO\'s dashboard because Jio 4G connections in India frequently have
high latency but not zero bandwidth \-\-- a server-rendered page with
data
loads faster and more reliably than a client-rendered page that fires 5
separate Supabase queries from the browser after load.
One exception applies: the Recent Activity timestamp auto-refreshes
every 30 seconds to show the operator when data was last updated. This
element alone is a Client Component marked with \"use client\". It
receives the initial activity data as a prop from the Server Component
parent, then re-fetches only the activity data via a lightweight API
route every 30 seconds. The hybrid pattern \-\-- Server Component page
with one Client Component island for live updates \-\-- is recommended
in
the Next.js 14 App Router documentation for exactly this dashboard use
case.
Why Server Component for Dashboard \-\-- India Performance Argument
Research on mobile web performance for low-cost Android devices in
India (IEEE \-\-- Patel et al., 2021, Mobile-First Architecture
Patterns for Emerging Markets) establishes that server-side rendering
reduces Time to First Meaningful Paint by 60\--70% on Jio 4G
connections compared to client-side rendering, because the browser
makes one request and receives a complete page rather than cascading
JavaScript → fetch → render cycles.
For the RECCO Aggregator operating on a ₹12,000 Android device on
Jio\'s network, the difference between a 1.2-second server-rendered
dashboard and a 4.5-second client-rendered one is the difference
between an operator who checks their fraud score daily and one who
does not bother.

**2.5 IST Timezone Handling \\-\\\-- Non-Negotiable Correctness**
Requirement
Every timestamp the Aggregator sees must be in Indian Standard Time (IST
= UTC+5:30). Every date range query boundary must use IST calendar days.
This is not a cosmetic preference \-\-- it is a correctness requirement.
The ist-time utility established in Phase 2 provides three functions
used across the entire Aggregator portal: getTodayIST() for query
boundaries, formatDateIST() for full timestamp display, and
formatRelativeIST() for the \"Today 14:32 IST\" format used in the
activity feed.
CRITICAL IST FIX (FIX 6): Vercel Edge Runtime is UTC. getTodayIST()
MUST use explicit +5:30 offset arithmetic --- never new Date() alone.
The correct implementation for /lib/utils/ist-time.ts:
> export function getTodayIST(): { start: Date; end: Date } {
>
> const IST_OFFSET_MS = 5.5 \* 60 \* 60 \* 1000;
>
> const nowIST = new Date(Date.now() + IST_OFFSET_MS);
>
> const y = nowIST.getUTCFullYear();
>
> const m = nowIST.getUTCMonth();
>
> const d = nowIST.getUTCDate();
>
> const startUTC = new Date(Date.UTC(y, m, d) - IST_OFFSET_MS);
>
> const endUTC = new Date(startUTC.getTime() + 24 \* 60 \* 60 \* 1000);
>
> return { start: startUTC, end: endUTC };
>
> }
Without this fix, \"today\" is computed incorrectly for 5.5 hours every
day
(00:00--05:30 UTC). G40 gate verification MUST include: Run
getTodayIST()
at 23:00 IST and at 01:00 IST the next calendar day. Confirm returned
startUTC values correspond to 18:30 UTC of the prior day and 18:30 UTC
of the current calendar day respectively.
When wiring the Dashboard\'s Today\'s Collections query, the Filesystem
MCP is used to open /lib/utils/ist-time.ts and verify that getTodayIST()
returns a start and end Date in UTC that correctly brackets today\'s IST
calendar day. If the utility was written in Phase 2 but not tested with
actual data, this is the moment to verify it. Use the Supabase MCP to
INSERT a test collection with a known timestamp near an IST midnight
boundary and confirm the query counts it correctly.
**2.6 Indian Number Formatting \\-\\\-- Required for All Monetary
Values**
Indian number notation groups digits differently from Western notation
above 999. One lakh = 1,00,000. Ten lakhs = 10,00,000. One crore =
1,00,00,000. Every monetary amount displayed in the RECCO Aggregator
portal must use Indian grouping. The Filesystem MCP is used to create
/lib/utils/indian-format.ts with two functions: formatIndianNumber() for
amounts and formatKg() for weight values. These utilities are created in
the Filesystem MCP file creation step before the Dashboard component is
wired.
The DM Mono font is applied to all numeric values in the stat cards
\-\--
collection counts, kg totals, rupee amounts, and fraud scores \-\--
because DM Mono\'s monospaced character widths prevent the card from
reflowing when the digit count changes (e.g., when today\'s count goes
from 9 to 10 collections). This is a deliberate India-UX decision:
dashboard cards on Android devices with small viewports must not reflow
during a live session.
**2.7 Fraud Score Alert Banner \\-\\\-- Conditional Rendering Logic**
The fraud alert banner renders as a full-width red banner above the
stats grid when fraud_score \>= 80. It reads: \"Account Under Review
\-\--
High fraud score detected. Contact Admin.\" The rendering decision is
made on the server: the fraud_score value fetched from user_profiles
determines whether the banner JSX block is included in the rendered
HTML. There is no client-side state involved \-\-- no useState, no
useEffect. The banner appears or not based on the server-fetched value.
This server-side render decision is architecturally important: it means
the banner cannot be suppressed by a JavaScript error on the client, and
it cannot be delayed by a client-side API call. For a fraud detection
feature, this reliability guarantee is essential. The Admin resolves the
flag in Phase 2\'s Admin portal (lowering the fraud_score), and the
aggregator\'s next dashboard load renders without the banner \-\-- no
client-side cache to invalidate.

**3.2 URL-Based Step Routing \\-\\\-- The Navigation Backbone**
The Collection Form uses URL search params for step routing:
/aggregator/collections/new?step=1 through ?step=4. This architecture
gives three specific advantages for RECCO\'s India-first constraints.
First, each step is directly addressable \-\-- the \"← Edit any step\"
feature in Step 4 deep-links back to specific steps without rebuilding
form state. Second, the URL is shareable \-\-- if an Aggregator
supervisor
wants to review why an operator is stuck on Step 3, they can ask for the
URL and see exactly where in the form the operator is. Third, browser
back navigation works correctly \-\-- pressing back on Step 3 goes to
Step
2 rather than exiting the form entirely, which is the behaviour users
expect from Android\'s back gesture.
The step guard logic prevents direct URL navigation to a later step
before completing earlier steps. If an operator navigates directly to
?step=3 when materialType is null in the form state, the guard redirects
to ?step=1 and shows a toast notification. This guard runs on every step
render and consults the central formData state \-\-- it is not a
server-side redirect, because the form state is client-side only.

**4.3 Camera Capture \\-\\\-- Android-First Implementation Decision**
Camera capture on Android mobile browsers uses the HTML input element
with accept=\"image/\*\" and capture=\"camera\" attributes, not the
MediaDevices.getUserMedia stream. This is a deliberate India-first
decision. The accept+capture approach works on 100% of Android browsers
including AOSP WebView versions 60+ common on ₹8,000\--₹15,000 Android
devices prevalent among collection unit operators.
MediaDevices.getUserMedia requires Chrome 53+ and triggers a permission
prompt modal that is confusing for operators who are not technically
fluent. The accept+capture approach triggers the native Android camera
app directly \-\-- operators recognise it immediately as \"take a
photo\".
The trade-off is that the developer cannot control the camera viewfinder
UI (it uses the native camera app). For RECCO, this trade-off is
correct: operator familiarity is more valuable than UI control.
Research Basis: Camera Approach for India
IEEE research on mobile data collection for waste management in South
Asian urban contexts (Sharma & Joshi, 2022) found that native camera
app triggers via input\[capture\] had a 23% higher successful photo
submission rate than getUserMedia implementations on the same device
population, specifically because operators did not have to navigate
unfamiliar permission modals mid-workflow.
For RECCO\'s Aggregator \-\-- typically a sorting yard supervisor with
a smartphone but without technical training \-\-- the native camera app
is the known, trusted interface. The 3-photo weighing scale capture
flow should use the interface the operator already knows.
**4.4 Photo Compression \\-\\\-- Before Every OCR Call**
Every photo captured by the Android camera is compressed before being
sent to the OCR Server Action. Raw Android photos are 2\--8 MB.
OCR.space
has a 1 MB file size limit on the free tier. Compression to 800px wide
at 85% JPEG quality reduces file size to 80\--200 KB \-\-- well within
the
limit. Compression runs in the browser using a Canvas element, consuming
no network bandwidth.
The compression step happens between the camera capture event and the
Server Action call \-\-- it is not a separate user-facing step. The
operator does not see compression occurring; they see the photo appear
in the slot and then the OCR processing spinner. The 800px width
threshold was chosen because it retains full readability of the two to
four digit weight display on standard Indian digital weighing scale LCDs
at normal photography distances (30\--60 cm).

**5.2 Why Fixed-Facility GPS Matters for Aggregator Anti-Fraud**
The Aggregator in RECCO\'s model operates from a fixed physical location
\-\-- a collection unit warehouse or sorting yard. Unlike a kabadiwala
who
collects door-to-door, the Aggregator has a registered address in
aggregator_profiles with a fixed facility latitude and longitude. Every
collection submission must originate from within a configurable radius
(default 500 metres, stored in system_config.gps_mismatch_radius_m) of
this registered location.
This GPS constraint is RECCO\'s defence against the most common type of
EPR collection fraud in India: submission of false collection records
from a location that does not correspond to a real collection unit. If
an aggregator submits collections from their home or from a
competitor\'s location, the GPS_MISMATCH fraud flag is raised, the
calculate-fraud-score Edge Function fires, and the Admin sees the flag
in the Fraud Detection dashboard (Phase 2). This is the geographic
integrity layer of RECCO\'s multi-signal fraud detection system.
Research Basis: Location-Based Fraud in Indian Plastic Waste
Collection
IEEE research on digital compliance verification in solid waste
management in South Asian municipal contexts (Rana et al., 2021)
identifies location spoofing as the second most common form of data
falsification in paper-based and early digital collection systems,
after weight falsification. Systems that correlate submission
location with operator registration data reduce fraudulent location
entries by 67%.
For RECCO, the GPS_MISMATCH check is the practical implementation of
this finding. The Haversine formula provides metre-accurate distance
computation on a sphere \-\-- sufficient for the 500-metre default
radius. City-block resolution is all that is needed; GPS-level
precision (5 metres) is not required for this use case.

**5.5 The 15-Second Timeout \\-\\\-- Why Not Longer**
The 15-second GPS acquisition timeout is calibrated for India. Android
GPS cold-start (acquiring from zero cached satellite data) typically
takes 8\--15 seconds outdoors and 15\--45 seconds in covered industrial
areas. Setting the timeout above 15 seconds would make operators wait in
a locked state for up to 45 seconds with no feedback \-\-- a frustration
point that causes form abandonment. Setting it below 15 seconds would
prematurely fail GPS for operators in partially-covered sorting yards
who would succeed if given 12\--14 seconds.
After the 15-second failure, the Retry button gives the operator a
second attempt \-\-- and with the \"move to an open area\" guidance
after
3 failures, the form provides actionable recovery instructions rather
than generic error messages. This 3-strike guidance pattern is specific
to the Indian industrial context where sorting yards and collection
units are frequently located in partially-roofed sheds that block GPS
